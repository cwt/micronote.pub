## Defect Description

`_cache` at [app.py:372-381](../../src/micronote/app.py#L372-L381) stores the fully-rendered HTML response body in `DB.cache2`:

```python
def _cache(resp, type_="html", arg=None):
    ...
    DB.cache2.update_one(
        {"path": request.path, "type": type_, "arg": arg},
        {"$set": {"response_data": resp, "date": datetime.now(UTC)}},
        upsert=True,
    )
```

`_get_cached` at [lines 360-369](../../src/micronote/app.py#L360-L369) returns `cached["response_data"]` directly as the HTTP response. The cache key is `f"{older_than}:{newer_than}"` — it does not incorporate the content of the notes themselves.

The render pipeline (`clean` filter → `bleach.clean`) sanitizes note content at render time. However, the pinned-note query at [app.py:405-412](../../src/micronote/app.py#L405-L412) returns all pinned docs, and their content flows through `display_note` which applies `clean` (bleach). So the stored HTML is post-sanitization — this is safe **as long as** the bleach filter runs on every note before caching.

The vulnerability is: the cache TTL is controlled by `DB.cache2.create_index("date", expireAfterSeconds=3600 * 12)` (12 hours). During those 12 hours, a note that is **unpinned and repinned** with different content (via the admin pin API, which does not invalidate `cache2`) will serve stale cached HTML. Conversely, a new pinned note posted after the cache was written will not appear until the cache expires.

More critically: `tasks.invalidate_cache` at [tasks.py:76-90](../../src/micronote/tasks.py#L76-L90) is called by `finish_post_to_inbox` but **not** by `finish_post_to_outbox` for pin/unpin operations. Pinning a note (which changes `meta.pinned` on the Create doc, not the note content) does not trigger `DB.cache2.delete_many({})` — the pin API endpoint at [api.py:161-171](../../src/micronote/api.py#L161-L171) calls `DB.activities.update_one` directly without touching `cache2`.

## Impact

- For up to 12 hours after a pin/unpin operation, the homepage serves stale content (new pinned notes missing, or unpinned notes still shown as pinned).
- If an attacker with admin access pins a note containing content that exploits a bleach bypass (e.g. a new XSS vector not in the bleach allow-list), the cached HTML will persist the exploit for 12 hours, amplifying the window of impact.
- The pin/unpin API should call `DB.cache2.delete_many({})` to keep the cache consistent.

## Remediation Plan

1. In `api_pin` and `api_unpin` ([api.py:161-184](../../src/micronote/api.py#L161-L184)), add `DB.cache2.delete_many({})` after the `update_one` call.
2. Reduce the cache TTL from 12h to a shorter window (e.g. 30s) or make it configurable.
3. Document that the page cache is content-blind and can serve stale notes for up to the TTL.
