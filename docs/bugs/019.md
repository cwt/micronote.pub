# _PENDING_CACHE_JOBS Uses Tuple Key with Inconsistent Shape Across Call Sites

## Defect Description

`_enqueue_media_cache` at [filters.py:85](../../src/micronote/filters.py#L85) computes:

```python
cache_key = (kind, url)
if cache_key in _PENDING_CACHE_JOBS:
    return
_PENDING_CACHE_JOBS[cache_key] = True
```

The key is `(Kind, url)` — no size dimension. However, `MEDIA_CACHE.get_file(url, size, kind)` at [line 120](../../src/micronote/filters.py#L120) looks up by `(kind, url, size)`. For `Kind.ATTACHMENT`, two sizes are stored: `None` (original) and `720` (thumbnail). `Kind.ACTOR_ICON` stores sizes `50` and `80`.

When the cache is cold and a page renders both the thumbnail and the full-size attachment for the same URL, the first call enqueues a `cache_media_item` job with `kind=ATTACHMENT` (size is not part of the job payload — see [worker.py:541-551](../../src/micronote/worker.py#L541-L551), which calls `MEDIA_CACHE.cache(url, kind)` without a size argument). The second call for the other size finds `(kind, url)` already in `_PENDING_CACHE_JOBS` and skips — this is correct.

But `cache_attachment` in [media.py:137-153](../../src/micronote/utils/media.py#L137-L153) stores **both** sizes in a single call:

```python
def cache_attachment(self, url: str) -> None:
    if self.get_file(url, None, Kind.ATTACHMENT) or self.get_file(url, 720, Kind.ATTACHMENT):
        return
    ...
    self._store(..., url, None, ...)   # original
    self._store(..., url, 720, ...)    # thumbnail
```

So the dedup key `(Kind.ATTACHMENT, url)` is consistent with what the worker does. The key is actually correct. The real issue is different: `cache_og_image` (size=100), `cache_actor_icon` (sizes 50, 80), and `cache_custom_emoji` (size=None) all have their own distinct `Kind` values, so `(kind, url)` is unique per kind. There is no cross-kind collision.

**Actual confirmed issue**: The `DB.jobs.find_one` check at [filters.py:92-100](../../src/micronote/filters.py#L92-L100) queries:

```python
existing = DB.jobs.find_one(
    {
        "type": "cache_media_item",
        "iri": url,
        "status": {"$in": ["pending", "processing"]},
    }
)
```

This query does not filter by `kind`. If a `cache_media_item` job for `url` with `kind=ACTOR_ICON` is already pending, a new `kind=ATTACHMENT` job for the same URL is skipped, and the attachment is never cached. Conversely, if the attachment job was enqueued first, the actor icon job for the same URL is silently dropped.

## Impact

- Under concurrent cold-cache rendering of a note that has both an attachment and an actor icon at the same URL (rare but possible with self-hosted instances that serve icons from the same CDN path), one of the two kinds is never cached.
- The `_PENDING_CACHE_JOBS` in-memory guard is also kind-blind: `(kind, url)` is in the guard, but the DB query is not, so the two layers disagree.

## Remediation Plan

Add the `kind` value to the DB dedup query:

```python
existing = DB.jobs.find_one(
    {
        "type": "cache_media_item",
        "iri": url,
        "payload.kind": kind.value,
        "status": {"$in": ["pending", "processing"]},
    }
)
```
