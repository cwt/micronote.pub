## Defect Description

Three modules each run:

```python
back = activitypub.MicroblogPubBackend()
ap.use_backend(back)
MY_PERSON = ap.Person(**ME)
```

- `app.py` lines 45-48
- `api.py` lines 35-38
- `tasks.py` lines 14-18

`MicroblogPubBackend.__init__` at [activitypub.py:150-152](../../src/micronote/activitypub.py#L150-L152) calls `create_db_client(DB_NAME)` and stores it on the instance. `ap.use_backend(back)` registers each module's own `back` instance as the active backend for the `active_boxes` global.

Because `app.py` is imported first (Flask app setup), its `back` is the one registered with `ap`. When `api.py` and `tasks.py` are subsequently imported, they overwrite the global backend with their own instances. The result is that **at runtime the active backend is whichever was imported last**, and `DB` access through `ap.get_backend()` goes to that module's backend instance.

Each `MicroblogPubBackend` instance holds its own `_ThreadLocalDB` proxy. The `create_db_connection()` function is thread-local, so all three backends actually share the same underlying SQLite connection within a given thread. The practical impact is limited, but:

1. The three `MY_PERSON` objects are distinct `ap.Person` instances — if any code path compares them by identity (`is`) rather than by `id`, behavior diverges.
2. `tasks.post_to_outbox` calls `back.save()` and `back.random_object_id()` on its own `back`, while `worker.finish_post_to_outbox` calls `back.outbox_create()` on the `back` imported from `tasks` — this is the `tasks.back`, which is a different Python object than `app.back`, even though both wrap the same thread-local DB connection.
3. The triple instantiation is confusing and makes it non-obvious which backend instance is "the" backend at any point in the call stack.

## Impact

- Maintenance hazard: a developer modifying `app.back` in one module does not affect `api.back` or `tasks.back`.
- If `MicroblogPubBackend.__init__` ever acquires state that is not shared via the thread-local DB (e.g. a `self._http_client`), the three instances will have divergent state.
- `ap.use_backend` is called three times at import; the last import wins. `worker.py` imports from `tasks`, so in a worker process `tasks.back` is the registered backend. In a web process `app.back` is registered first, but `api.blueprint` import (inside `app.py`) calls `api.py`'s module-level `ap.use_backend(api.back)`, so the **web process** ends up with `api.back` as the active backend, not `app.back`.

## Resolution

- Created [src/micronote/instance.py](../../src/micronote/instance.py):
  - Centralized single instantiation of `MicroblogPubBackend()`, registered it with `ap.use_backend(back)`, and instantiated `MY_PERSON = ap.Person(**ME)`.
- Updated [src/micronote/app.py](../../src/micronote/app.py):
  - Removed duplicate local `back` and `MY_PERSON` instantiations; imported `MY_PERSON` and `back` from `micronote.instance`.
- Updated [src/micronote/api.py](../../src/micronote/api.py):
  - Removed duplicate local `back` and `MY_PERSON` instantiations; imported `MY_PERSON` and `back` from `micronote.instance`.
- Updated [src/micronote/tasks.py](../../src/micronote/tasks.py):
  - Removed duplicate local `back` and `MY_PERSON` instantiations; imported `MY_PERSON` and `back` from `micronote.instance` (re-exporting them for worker compatibility).
- Added unit tests in [tests/test_instance_singleton.py](../../tests/test_instance_singleton.py) asserting that `back` and `MY_PERSON` are identical objects (`is`) across `app`, `api`, `tasks`, `worker`, and `instance`.
