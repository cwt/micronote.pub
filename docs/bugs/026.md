## Defect Description

Follow-up to BUG-025: the deterministic YouTube card only covered **video** URLs (`youtu.be/<id>`, `watch?v=`, `/shorts/`, `/embed/`, `/live/`). A note whose link is a **channel** URL (e.g. `https://youtube.com/@babylon5` in outbox note `ea3485916349a141`) still stores `meta.og_metadata = []` and renders no card.

## Root Cause

No stable, deterministic source of channel metadata exists from a datacenter egress IP:

| Source | Result |
| --- | --- |
| Channel page (`youtube.com/@babylon5`) | Same consent-gated JS shell as the watch page (BUG-025) — no `og:` tags |
| `GET https://www.youtube.com/oembed?url=https://www.youtube.com/@babylon5&format=json` | `404 Not Found` — oEmbed supports video URLs only (verified from `cwt-02`) |
| Channel avatar | Served from `yt3.ggpht.com` under a hashed URL that is not derivable without scraping the consent-gated page |

So the generic scrape path drops the link (same silent `if data.get("url")` drop as BUG-025), and no card is stored.

## Impact

- Channel links render as plain links with no preview. Low severity: the link works; only the preview is missing, and no avatar can be shown anyway.
- A secondary latent issue: the link-card template rendered an unconditional `<img src="{{ og.image | get_og_image_url }}">`, so any card without an `og:image` (including ordinary scraped sites that omit it) would render a broken image element.

## Resolution

Added a channel branch to the YouTube short-circuit in [opengraph.py](../../src/micronote/utils/opengraph.py):

- `_youtube_channel(url)` — recognizes the `/@handle`, `/channel/<id>`, `/user/<name>`, and `/c/<name>` forms (any of the YouTube hosts; `youtu.be` is video-only).
- `_youtube_channel_card(canonical, title)` — a fully deterministic **text-only** card: `title` = handle or name when the URL carries one, else "YouTube channel"; `description` = "YouTube channel"; no `image` key (an avatar cannot be derived without the consent-gated page).

Supporting changes:

- `fetch_og_metadata` now tries the video card, then the channel card, before falling through to the generic scrape — so channel URLs never hit the consent-gated page or a wasteful AP `lookup()`.
- [templates/utils.html](../../src/micronote/templates/utils.html): the `<img>` in the `og-link` card is now conditional on `og.image` being present (fixes the latent broken-image case and renders channel cards without a thumbnail).
- [handlers.py](../../src/micronote/handlers.py#L185-L191) already skips image caching when `og.get("image")` is falsy, so text-only cards need no handler change.

Tests in [tests/test_opengraph.py](../../tests/test_opengraph.py): channel URL variants (handle / channel id / user / c, plus non-channel URLs returning `None`) and the deterministic text-only card, asserting **no** `requests.get` call is made for channel links.

## Deployment note

Requires a redeploy of `cwt-02`. After deploying, re-run the backfill (`scripts/backfill_og.py`, default scope matches any note containing a `youtu`/`youtube` substring, so channel-link notes are covered):

```sh
podman exec -i micronote-worker python - < scripts/backfill_og.py
```

Known example affected note: `outbox/ea3485916349a141` (links `youtube.com/@babylon5`).
