## Defect Description

In `_handle_replies` ([src/micronote/activitypub.py#L490-L535](../../src/micronote/activitypub.py#L490-L535)):

```python
root_reply = in_reply_to
try:
    reply = ap.fetch_remote_activity_sync(root_reply)
except (ActivityGoneError, ActivityNotFoundError, NotAnActivityError):
    logger.info(f"reply target {root_reply} not fetchable, skipping thread walk")
    return
...
while reply is not None:
    ...
    try:
        reply = ap.fetch_remote_activity_sync(root_reply)
    except (ActivityGoneError, ActivityNotFoundError, NotAnActivityError):
        logger.info(f"reply target {root_reply} not fetchable, stopping thread walk")
        break
```

When an incoming activity arrives in the inbox that is in reply to a remote post requiring authorized fetch (HTTP 401 Unauthorized, such as instances with `AUTHORIZED_FETCH=true`), or a remote server returning 403, 500, 502, 503, or connection timeouts:
`ap.fetch_remote_activity_sync()` raises `active_boxes.errors.ActivityUnavailableError`:

```text

    back.inbox_create(MY_PERSON, activity)
```

Because `ActivityUnavailableError` (and generic `active_boxes.errors.Error` / network exceptions) is omitted from the `except` tuple, the exception escapes `_handle_replies` and crashes `finish_post_to_inbox`.

---

## Impact

- The background worker fails the `finish_post_to_inbox` job.
- The task is retried 9 times with exponential backoff and ultimately abandoned as failed.
- Legitimate incoming replies and mentions cannot be processed into the inbox whenever any upstream post in the thread cannot be dereferenced by anonymous HTTP GET requests.

---

## Root Cause Analysis

`_handle_replies` only catches `(ActivityGoneError, ActivityNotFoundError, NotAnActivityError)`. It fails to catch `ActivityUnavailableError`, `Error`, or other network/HTTP exceptions raised by `fetch_remote_activity_sync`.

---

## Remediation Plan

1. Catch `(Error, Exception)` in `_handle_replies` both during initial root reply fetch and within the thread traversal loop.
2. If the initial fetch fails, still update `meta.count_reply` / `meta.count_direct_reply` if `in_reply_to` exists in local DB, and set `meta.thread_root_parent` on the `Create` activity without crashing.
3. If thread traversal fails mid-way, cleanly stop traversal and persist `meta.thread_root_parent` with the furthest resolved parent.

---

## Resolution

- In [src/micronote/activitypub.py](../../src/micronote/activitypub.py), updated `_handle_replies` to catch `(Error, Exception)` across both initial and looped remote reply fetches.
- Imported `ActivityUnavailableError` to ensure explicit coverage.
- If upstream remote reply fetch fails due to 401 Unauthorized (e.g. `AUTHORIZED_FETCH=true`), 403, 500, 503, or network errors, `_handle_replies` logs an informational message and skips thread walking without propagating an unhandled exception or aborting the job.
- Still increments reply counters if `in_reply_to` is a locally cached note and sets `meta.thread_root_parent` to `root_reply`.
- Added unit tests in [tests/test_reply_handling.py](../../tests/test_reply_handling.py) verifying error suppression, fallback behavior, and partial thread traversal resilience.
