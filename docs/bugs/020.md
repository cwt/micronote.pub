## Defect Description

`inject_config` at [app.py:87-131](../../src/micronote/app.py#L87-L131) is registered with `@app.context_processor`, so it runs on **every** template render — including pages that don't display any of these counts. It issues 5 separate `count_documents` calls:

1. `notes_count` (line 95)
2. `with_replies_count` (line 99)
3. `liked_count` (line 102)
4. `followers_count` (line 125, inline)
5. `following_count` (line 126, inline)

Only `header.html` (included in `index.html`, `note.html`, `stream.html`, etc.) actually displays these values. Pages like `/robots.txt`, `/nodeinfo`, `/manifest.json`, `/outbox`, and API endpoints that call `render_template` for error pages all pay the 5-count cost.

With NeoSQLite, each `count_documents` is a full table scan on the `activities` collection. With a large inbox (tens of thousands of docs) this adds ~50-200ms to every request.

## Impact

- Every non-cached HTML page carries 5 unnecessary full-collection scans.
- The counts are only rendered in the header, which is included on ~8 templates; the remaining ~14 routes pay the cost for nothing.
- Under gunicorn with multiple workers, the concurrent scan load amplifies.

## Remediation Plan

- Split the context processor: register a lightweight `inject_config` that only provides `config`, `me`, `micronote_version`, `logged_in` (no DB queries).
- Move the 5 count queries into a separate `@app.context_processor` that is explicitly included only where needed, or compute them in `header.html`'s template context via a custom Jinja global.
- Alternatively, cache the counts in `DB.cache2` with a short TTL (e.g. 30s) and read from cache in the context processor.
